# AGENT-TASKS.md — the standing contract for anyone executing a ticket

**Этот файл — стоячие правила работы с проектом. Он читается первым, до первой правки, при
выполнении любой задачи из `.scratch/site-development/issues/`.** Правила ниже не зависят от того,
какой сегодня тикет: они одинаковы для всех. Специфика задачи лежит в файле самой задачи.

**Пишет этот файл только планер.** Исполнитель его не редактирует, не «уточняет» и не дополняет —
даже если по ходу работы нашёл в нём неточность. Нашёл — сообщи в отчёте.

Файл переживает перевыкат харнесс-базы: `.dsh/AGENTS.md` перерисовывается из базы, а этот файл —
собственность проекта и лежит рядом.

## 0. Как владелец выдаёт задачу

Владелец передаёт исполнителю **только путь к файлу задачи**, например
`.scratch/site-development/issues/06-architecture-tests-unit-tests-ci.md`. Ничего больше объяснять не
нужно: в файле задачи написано, что делать, а первая же ссылка в нём ведёт сюда, где лежат ветки,
команды и критерий готовности.

Признак того, что исполнитель делает что-то не так: он спрашивает про ветки, про команды, про
расширение доступа к песочнице или про то, что можно и нельзя трогать. Ответ на всё это — здесь, а
не в переписке.

## 1. Прочитай до первой правки

1. `.dsh/AGENTS.md` — правила проекта: архитектура, дисциплина анализаторов, тесты, инструменты.
   Это контракт, а не рекомендации.
2. `WORKFLOW.md` — команды сборки, тестов и базы, и раздел «Definition of done».
3. `.scratch/site-development/map.md` — карта: назначение, стоячие решения, что уже решено.
4. **Файл своей задачи** — `.scratch/site-development/issues/<NN>-<slug>.md`. Он и есть задание:
   там написано, что делать, что нельзя трогать и по какому критерию задача считается сделанной.

Если файл задачи и этот файл расходятся — **прав этот файл**.

## 2. Скиллы

Правило проекта: если задача попадает в область скилла — скилл **загружается**, а не вспоминается.
Механика — раздел «Skills» в `.dsh/AGENTS.md`.

- Есть инструмент загрузки скиллов (в DSH это `skill`) — загрузи те, что названы в файле задачи.
- Инструмента нет — прочитай `.dsh/skills/<имя>/SKILL.md` напрямую. Рядом со скиллом бывают
  дополнительные файлы (`ADR-FORMAT.md`, `CONTEXT-FORMAT.md`, `DEEPENING.md` и подобные) — они
  читаются по ссылкам внутри `SKILL.md`.

## 3. Git

- **Ветка — первым действием, до первой правки.** Одна задача — одна ветка от **`develop`** (это
  рабочая ветка проекта; `master` отстаёт и в работу не берётся). **Имя ветки: `feature/<slug>`, где
  `<slug>` — имя файла задачи без номера и без расширения.** Пример: задача
  `issues/06-architecture-tests-unit-tests-ci.md` → ветка `feature/architecture-tests-unit-tests-ci`.
  Проверить, от чего ветвишься: `git log --oneline -1 develop` — в истории должна быть видна работа
  по этому проекту, включая этот контракт. Если её не видно, ты смотришь на устаревшую ветку —
  остановись и скажи об этом.
- Права на git: **читать — свободно** (`git status`, `git diff`, `git log`, `git show`, `git blame`),
  **писать — только в свою ветку** (`git checkout -b`, `git add` файлов своей задачи, `git commit`).
  Всё остальное — владельца: `push`, `merge`, `rebase`, `reset`, `checkout` чужих веток, теги.
- Никаких других имён веток (никаких `chore/`, `docs/`, `fix/`, никаких тикет-номеров в имени) —
  шаблон один, чтобы владельцу было видно, что это ветка задачи.
- **Коммить** в эту ветку. Сообщения — как в истории репозитория: по-русски, с префиксом.
- **Никогда не пушить.** Ни `git push`, ни `--force`, ни `git merge` в `master`/`develop`, ни pull
  request. Пуш и слияние — владельца.
- **Не делать `git fetch`/`git pull` у `origin`**: доступ к GitHub по SSH в этой среде не настроен,
  команда падает с `Permission denied (publickey)`. Работай от локального `master`; если он
  расходится с `origin/master` — это забота владельца, «исправлять» не надо.
- Чужие ветки не трогать. Коммить только файлы своей задачи; чужие незакоммиченные изменения не
  добавлять.
- Каталог `.scratch/` тебе не принадлежит. Единственное исключение — в конце ты дописываешь
  `## Answer` и `Status: resolved` в файл **своей** задачи. `map.md` не редактируй: строку в
  «Decisions so far» дописывает планер.

## 4. Среда

- **Команды запускаются в режиме `workspace-write`, и в этом режиме ничего не падает.** ACL на
  рабочую папку выдан один раз владельцем (см. § 14), поэтому `pwsh`, `dotnet`, `docker`, `git`
  работают обычно. Расширение доступа запрашивать не нужно.
- Если `pwsh` всё же падает с `SetNamedSecurityInfoW failed (Win32 5): grantWrite(<путь>)` — песочница
  не смогла выдать себе права на запись в рабочую папку. **Это не ошибка твоей команды** и не повод
  её переписывать. Лечится один раз и владельцем — **останови работу и напиши владельцу одну
  строку**: владелец рабочей папки — чужой SID, `WRITE_DAC` у процесса нет, нужно повторить шаг из
  § 14. Не ищи обходных путей и не подменяй команды.
- Провал команды из-за окружения (**нет демона Docker, не поднялась база, недоступен NuGet,
  не установлен инструмент**) — это не «не получилось»: напиши, что именно не поднялось, какой
  командой это проверить и что нужно сделать владельцу. Не выдумывай обходной путь.

## 5. Команды

Все команды выполняются из каталога `backend/` (там `global.json` и решение `MySite.slnx`).

| Команда | Зачем | Ожидаемый результат |
|---|---|---|
| `dotnet build MySite.slnx -m:1` | сборка | `Предупреждений: 0, Ошибок: 0`, код возврата 0 |
| `dotnet build MySite.slnx -m:1 --no-restore` | быстрая сборка, когда пакеты уже восстановлены | то же |
| `dotnet restore MySite.slnx -m:1` | восстановление пакетов, если в кэше их нет | код возврата 0 |
| `dotnet test MySite.slnx` | штатный прогон тестов (владелец, CI) | зелёные тесты, код возврата 0 |
| `dotnet tests\MySite.UnitTests\bin\Debug\net10.0\MySite.UnitTests.dll` | **быстрый путь для исполнителя:** прямой запуск собранной тестовой сборки; свои числа отдаёт каждая сборка отдельно | итоговая таблица `Total / Failed / Succeeded`, код возврата 0 |
| `docker compose up -d` | поднять PostgreSQL (порт 5433) | контейнер `mysite_postgres` в состоянии `Up` |
| `docker compose ps` | проверить, что контейнеры подняты | строка со статусом `Up` |
| `docker compose exec -T postgres pg_isready -U postgres -d MySite` | база принимает соединения | `accepting connections` |
| `dotnet ef migrations list -p src/MySite.Infrastructure.Postgres -s src/MySite.Web` | какие миграции накатаны | `(Pending)` или список применённых |
| `dotnet ef database update -p src/MySite.Infrastructure.Postgres -s src/MySite.Web` | накатить миграции на локальную базу | `Done.`, код возврата 0 |
| `dotnet ef migrations add <Name> -p src/MySite.Infrastructure.Postgres -s src/MySite.Web` | **создать** новую миграцию | новый файл и обновлённый снапшот |

Обязательные оговорки:

- `-m:1` при сборке обязателен: многопроцессная сборка открывает именованные каналы, которые
  песочница блокирует. Сборка должна быть чистой: `TreatWarningsAsErrors` включён, предупреждение =
  ошибка.
- `dotnet test` из корня репозитория падает («VSTest target is no longer supported») — только из
  `backend/`.
- `dotnet ef` печатает предупреждение «tools version 10.0.9 is older than runtime 10.0.12». Это шум,
  не ошибка; из-за него не меняй версии инструментов.
- Пока в проекте нет тестов, `dotnet test` сообщает «Запущено ноль тестов» и возвращает код **8**
  (`Microsoft.Testing.Platform`, раннер задан в `backend/global.json`). Это не сбой, но и не
  «зелёные тесты»: прямой запуск сборки в этом состоянии даёт код 0, а «ноль» видно по таблице
  `Total: 0`. После первого теста (тикет 06) критерий один: все прогоны успешны, сбоев нет, код 0.
- Сборка печатает «Ошибок: 0», но возвращает код 1 и пустой вывод — это признак сломанного restore.
  Сообщи об этом владельцу: restore делает он.
- `dotnet format --verify-no-changes` в песочнице недоступен (команда открывает workspace через
  MSBuild и требует restore). Стиль всё равно проверяется: в `backend/Directory.Build.props` включён
  `EnforceCodeStyleInBuild=true`, поэтому нарушение форматирования приходит ошибкой сборки. Чистая
  сборка = чистое форматирование.
- Docker: `docker compose down` останавливает контейнер, `docker compose down -v` **уничтожает том с
  данными**. Флаг `-v` применяется только тогда, когда владелец это разрешил (или когда файл задачи
  прямо говорит, что база одноразовая).

## 6. Миграции

- Миграция **генерируется командой**; файлы миграций руками не пишутся и не правятся. Нужна новая
  схема — `dotnet ef migrations add`, одна миграция на одно связное изменение.
- Накатывание на локальную базу — `dotnet ef database update`. Сначала убедись, что контейнер
  поднят и `pg_isready` отвечает.
- Для задачи, которая меняет схему, критерий готовности включает: миграция сгенерирована, накатана
  на локальную базу, `dotnet ef migrations list` не показывает `(Pending)`, сборка чистая, тесты
  зелёные.
- Если `database update` падает из-за расхождения схемы с историей миграций (например
  `42P07: relation "<table>" already exists` — том собран старой миграцией) — **не чини это
  вручную и не пересоздавай том молча**. Останови работу, опиши ошибку и спроси владельца:
  пересоздание тома уничтожает локальные данные.
- На живую (не локальную) базу миграции накатывает владелец.

## 7. Где граница исполнителя

**Исполнитель делает всё, что нужно для зелёного результата на локальной машине:**

- пишет код, тесты и документы;
- собирает: `dotnet build MySite.slnx -m:1`;
- **Запускать тесты.** Либо прямой запуск собранной сборки — он быстрее и печатает точные числа,
  либо `dotnet test`:

```powershell
dotnet tests\MySite.UnitTests\bin\Debug\net10.0\MySite.UnitTests.dll
dotnet tests\MySite.ArchitectureTests\bin\Debug\net10.0\MySite.ArchitectureTests.dll
dotnet test MySite.slnx
```

- поднимает docker-контейнеры: `docker compose up -d`, проверяет `docker compose ps` и `pg_isready`;
- накатывает миграции на локальную базу: `dotnet ef database update`;
- генерирует то, что генерируется командой (миграции, сгенерированный API-клиент), вместо ручной
  правки сгенерированных файлов;
- на фронтенде — гоняет `lint`, `typecheck` и тесты теми командами, что записаны в `WORKFLOW.md`.

**Владельцу остаётся:** пуш и слияние в `master`/`develop`, ревью, решения о подавлении анализаторов
и о новых зависимостях, тексты сайта, живая (не локальная) база и деплой. Приложение
(`dotnet run`) поднимать не требуется, если файл задачи не просит об этом прямо.

**Запрещено, чем бы это ни оправдывалось:** глушить анализатор или правило линтера вместо починки
кода; править сгенерированные файлы руками; пушить; трогать чужие задачи и `map.md`; расширять
рамки своей задачи «попутно заметил и починил».

## 8. Известные ловушки анализаторов

Анализаторы включены на максимум (`TreatWarningsAsErrors`, `AnalysisMode=All`, четыре пакета), поэтому
любая находка — ошибка сборки. Порядок один: **сначала чинится код**; подавлять нельзя. Ниже —
повторяющиеся ловушки и рабочие рецепты, снятые прогонами.

| Код | Симптом | Что делать |
|---|---|---|
| `CA1305`, `CA1310`, `CA1311`, `CA1307` | работа со строками без культуры | `CultureInfo.InvariantCulture`, `ToUpperInvariant`/`ToLowerInvariant`, `StringComparison` |
| `CA1863` | строка формата создаётся каждый раз | кэшировать через `CompositeFormat` |
| `CA1716` | зарезервированное слово в имени типа | не называть типы `Shared`, `Error` и подобными |
| `MA0009` | регулярка без таймаута | `[GeneratedRegex(..., matchTimeoutMilliseconds: 1000)]` |
| `MA0023` | группы захвата там, где нужно только совпадение | `(?:...)` вместо `(...)` |
| `SYSLIB1045` | `new Regex(...)` в рантайме | `[GeneratedRegex]` в `partial`-классе, метод `private static partial` |
| `IDE0130` | namespace не совпадает с папкой | привести namespace к структуре каталогов |
| `IDE0055` и соседние | форматирование | сборка и есть проверка формата (`EnforceCodeStyleInBuild=true`) |

Рабочий рецепт `[GeneratedRegex]`, снимающий сразу `MA0009` и `MA0023` без `#pragma`:

```csharp
[GeneratedRegex("^[a-z0-9]+(?:-[a-z0-9]+)*$", RegexOptions.None, matchTimeoutMilliseconds: 1000)]
private static partial Regex SlugPattern();
```

Если анализатор всё-таки сработал так, что правкой кода не снимается, — **не подавляй и не отключай**.
Вынеси в отчёт: код правила, точный текст, файл и строку, оценка «единичный случай или массовый», и
предложение. Решение — владельца, запись — в реестр в `WORKFLOW.md`.

## 9. Критерий готовности

Задача закончена, когда **всё** ниже верно и подтверждено дословным выводом команд:

1. Сборка чистая: `dotnet build MySite.slnx -m:1` → 0 предупреждений, 0 ошибок.
2. Тесты зелёные: `dotnet test MySite.slnx` → код возврата 0, тесты задачи и все прежние проходят.
   Новая функциональность покрыта тестом подходящего уровня (unit / integration / architecture).
3. Если задача трогает схему — миграция сгенерирована и накатана, `(Pending)` не осталось.
4. Если задача трогает инфраструктуру — `docker compose ps` показывает `Up`, база отвечает.
5. Анализатор не заглушён: новых строк в `backend/.globalconfig` нет, подавлений без записи в
   реестр `WORKFLOW.md` нет.
6. Версия пакета живёт только в `backend/Directory.Packages.props`; `.csproj` — без `Version`.
7. Документация отражает изменение: `ARCHITECTURE.md` — если двинулась структура, контракт или
   стек; `.dsh/AGENTS.md` — не тобой (см. § 10).
8. **Шапка файла задачи переведена в `resolved`** (см. § 13): строка `Status:` в шапке заменена,
   а не дописана в тексте. Пока в шапке стоит `open`, задача для планера и карты открыта, каким бы
   полным ни был ответ.

## 12. Дисциплина ревью: замечание без решения не закрыто

Ревью и приёмку делает владелец (в другой сессии — скиллом `code-review`). Если замечание пришло
исполнителю, у каждого замечания есть **ровно одно** решение — до того, как задача считается
закрытой:

| Решение | Когда | Куда попадает |
|---|---|---|
| `fix` | замечание верное и входит в объём задачи | правка в ту же ветку + повторный отчёт в `## Answer` |
| `defer` | замечание верное, но вне объёма | отдельный тикет в `.scratch/site-development/issues/` (заводит владелец) со ссылкой на замечание |
| `reject` | замечание неверное | обоснование в файле задачи: факт, правило или ссылка на источник |

- Замечание без решения = задача не закрыта.
- Повторяющиеся и устаревшие формулировки правил удаляются: **одно правило — одна авторитетная
  формулировка**. История остаётся в git.
- Если замечание шире одного диффа — оно переносится в постоянное место: сначала тест, потом
  правило кода, потом `ARCHITECTURE.md`/ADR, потом тикет.

## 13. Отчёт и закрытие задачи

Верни коротко и по делу:

1. Имя ветки и хеши коммитов.
2. Список созданных, изменённых и удалённых файлов.
3. Дословный вывод сборки (строка про предупреждения и ошибки) и тестов (сколько прошло, код
   возврата).
4. Для задач про схему: вывод `dotnet ef migrations list` и `database update`.
5. Для задач про инфраструктуру: вывод `docker compose ps` / `pg_isready`.
6. Что осталось за пределами задачи; всё неочевидное или пошедшее не по плану; все находки, где
   документ и код расходятся.

### Как закрыть файл задачи

Ровно три действия, в этом порядке:

1. **Замени строку в шапке.** В файле задачи есть строка `Status: open` — её значение меняется на
   `resolved`:

   ```text
   Было:  Status: open
   Стало: Status: resolved
   ```

   Это единственное место, где живёт статус. **В тексте ответа слово `Status: resolved` не
   пишется** — дописанная в конце ответа строка статус не меняет.

2. **Заполни `## Answer`** вместо строки-заглушки `<!-- заполняется при закрытии -->`. Пиши по
   порядку: что сделано → чем подтверждено (дословные команды и их вывод) → файлы, ветка, коммиты →
   что осталось за рамками и какие вопросы требуют решения владельца. Ответ читает владелец, а не
   ты: он должен понять результат, не открывая код.

3. **Проверь себя:**

   ```powershell
   Select-String -Path .scratch\site-development\issues\<имя-твоего-файла>.md -Pattern '^Status:'
   ```

   Должно вернуть `Status: resolved`, и это должна быть строка из шапки — первая строка вывода.

Если задача выполнялась не до конца (остановка по условию, вопрос владельцу, невозможность
проверить) — статус **не** меняется на `resolved`: файл остаётся `open`, а причина и вопрос
пишутся в `## Answer`. Закрыть задачу может только полностью выполненная задача.

## 14. Одноразовая настройка машины (сделано владельцем)

Песочница DSH в режиме `workspace-write` перед запуском команды выдаёт себе ACE на рабочую папку
через `SetNamedSecurityInfoW`. Это получается только у **владельца** папки: право `WRITE_DAC`
неявно даётся владельцу и не входит в «Изменение»/`Modify`.

```
Владелец H:\CSharp\MySite\MySite_dev : S-1-5-21-2975921196-1521536798-1127005991-1001  (чужой SID)
Пользователь процесса                : S-1-5-21-929734596-2925668590-3631407417-1001  (ilya_pc\ilka)
```

Отсюда и падало всё, включая `Get-ChildItem`: песочница отказывается запускать процесс, если не
смогла выдать себе права. Лечение — одноразовое, в **повышенном** PowerShell:

```powershell
takeown /F "H:\CSharp\MySite\MySite_dev" /R /D Y
icacls "H:\CSharp\MySite\MySite_dev" /grant "$($env:USERNAME):(OI)(CI)M" /T
```

Альтернатива без консоли: свойства папки → «Безопасность» → «Дополнительно» → владелец → «Изменить»
→ выбрать свою учётную запись → «Заменить владельца подконтейнеров и объектов» → ОК.

Проверка, что всё в порядке (в обычном, не повышенном сеансе):

```powershell
(Get-Acl "H:\CSharp\MySite\MySite_dev").Owner   # должен быть SID пользователя, а не чужой
```

После этого `workspace-write` работает, и исполнителю ничего не нужно разблокировать. Если на другой
машине или после копирования папки ошибка вернётся — повтори шаг выше: это признак чужого владельца,
а не сломанного проекта.

Запасной вариант, если починить владельца нельзя: сессия целиком идёт в `danger-full-access`
(`/permission danger-full-access` в GUI или `DSH_PERMISSION_MODE=danger-full-access`) — этот режим
вообще не трогает ACL, но снимает и ограничения песочницы.
