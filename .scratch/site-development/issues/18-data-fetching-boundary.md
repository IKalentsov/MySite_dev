## Question

Два вопроса, которые до сих пор не были ни решением, ни тикетом:

1. **Открытый вопрос ADR-0004 про data fetching.** «Server Components, a query library, or a mix» —
   это решение определяет структуру каждого экрана, и при разметке карты я его пропустил.
2. **Ограничение, которое принёс тикет 10.** `async` Server Components **не тестируются** ни в
   Vitest, ни в Jest: оба официальных гайда Next.js говорят об этом прямо и советуют для них e2e.
   При этом правила проекта требуют интеграционный уровень «экран с подменённой сетью через MSW» и
   все четыре состояния. Если страница целиком состоит из async Server Component, этот уровень
   физически не на чем построить.

**Что решить:**

- Где проходит граница данных: async Server Component читает API напрямую, или данные достаёт
  тонкий слой, а экран получает их как пропсы.
- Что именно тогда тестируется Vitest'ом с MSW: синхронная презентационная часть плюс четыре
  состояния, а async-загрузка уходит в Playwright — или граница проводится иначе.
- Кэширование и ревалидация: `fetch` в Next.js, политика кэша, `generateStaticParams` из тикета 12.
- Нужна ли библиотека запросов на клиенте вообще, если данных пока две штуки и они только читаются
  (правило проекта: клиентское состояние — только для клиентских нужд, серверные данные не
  дублируются).
- Стыкуется с пунктом 2 тикета 10: MSW для RSC первоисточниками не подтверждён, поэтому граница
  должна позволять подставить данные, а не только перехватить сеть.

Ответ влияет на тикеты 15 (подключение клиента) и 16 (страница целиком).

## Answer

**Решение принято владельцем 2026-11-16.** Экран серверный, библиотеки запросов нет; тестируемая
граница — синхронный презентационный компонент на пропсах, а не `async` Server Component.

### 1. Где проходит граница данных

```
apps/web/src/app/[lang]/page.tsx        # тонкий route: реэкспорт экрана из _pages/home
apps/web/src/_pages/home/
├── index.ts                            # публичный API слайса: HomePage и типы
├── api/get-home-content.ts             # server-only: @mysite/api-client -> HomeContent
└── ui/
    ├── home-page.tsx                   # async Server Component: зовёт getHomeContent
    └── home-page-view.tsx              # синхронный view: HomeContent -> состояния
```

- `getHomeContent(lang)` — единственное место, которое знает про API. Она вызывает публичные
  функции `@mysite/api-client` (тикет 11), а не `fetch` по строке, и возвращает
  `HomeContent = { profile, projects, failed }`.
- `home-page.tsx` — тонкий async Server Component: получает `HomeContent`, при полном отказе
  бросает ошибку в `error.tsx`, иначе рендерит `HomePageView`.
- `home-page-view.tsx` — синхронный компонент без хуков и без сети: получает данные пропсами и
  реализует empty / success / partial. Именно он тестируется Vitest + RTL.
- Компоненты никогда не импортируют `@mysite/api-client` напрямую: правило «UI работает только
  через публичный API» соблюдено, публичный API здесь — `getHomeContent` и `HomePageView`.

### 2. Что тестируется чем

| Уровень | Что покрывает | Чем |
|---|---|---|
| Компонентный | `HomePageView`: success, empty, partial (один блок упал), доступные роли и текст | Vitest + RTL, данные — фикстуры-пропсы |
| Клиентский | `@mysite/api-client`: `getProfile`/`getProjects`, ошибки, `no-store` | Vitest + MSW на уровне запроса |
| E2E | Реальная страница: серверный путь данных, loading, error + retry, переключатель языка, fallback | Playwright против `next start` и локального API |

**MSW не применяется к `async` Server Components.** Тикет 10 уже установил: ни Vitest, ни Jest их
не поддерживают, а MSW для RSC первоисточниками не подтверждён. Поэтому «интеграция = экран с
подменённой сетью» для серверной страницы раскладывается на компонентный уровень (view на
пропсах) и E2E; MSW остаётся для клиентского слоя и будущих клиентских экранов. Это уточнение
правила проекта, его нужно внести в `.dsh/AGENTS.md` (Testing → Integration).

### 3. Четыре состояния и частичный результат

| Состояние | Где живёт | Что видит пользователь |
|---|---|---|
| Loading | `app/[lang]/loading.tsx` (Suspense) | Скелет на месте контента, без сдвига вёрстки |
| Error | `app/[lang]/error.tsx` (клиентская граница) | Понятный текст и кнопка повтора (`reset`) |
| Empty | `HomePageView` | «Пока ничего нет» — без белого экрана |
| Success | `HomePageView` | Профиль и проекты |
| Partial | `HomePageView` | Что пришло — показано; упавший блок помечен и имеет повтор |

`getHomeContent` делает два запроса через `Promise.allSettled`:

- оба упали → бросает `HomeContentError`, срабатывает `error.tsx`;
- один упал → возвращает `{ profile, projects, failed }`, и `HomePageView` показывает доступную
  часть с inline-ошибкой и повтором;
- оба успешны → обычный success/empty.

Повтор на клиенте — `router.refresh()` (тонкий клиентский компонент кнопки), без дублирования
серверных данных в клиентском состоянии.

### 4. Кэш и ревалидация

- `getHomeContent` ходит в API с `cache: "no-store"`; страница динамическая. Это согласуется с
  решением тикета 12: без `generateStaticParams`, без ISR, без статической генерации — в CI нет
  базы, а контент локальный.
- `revalidate` не используется: после пересидирования контент виден по обычному обновлению
  страницы. Появится живое обновление или CDN — это отдельное решение.
- `generateStaticParams` не добавляется (12).

### 5. Библиотека запросов не нужна

Данных две штуки, они только читаются на сервере. Query-библиотека добавила бы клиентское
состояние, кэш и слой, который нечем оправдать; правило «клиентское состояние — только для
клиентских нужд» нарушалось бы. Клиентское состояние остаётся у темы (`next-themes`) и у
transient UI вроде кнопки повтора.

### 6. Какие правила проекта приходится уточнить

1. `.dsh/AGENTS.md`, Testing → Integration: для серверной страницы уровень «экран с MSW» не
   существует; его заменяют компонентный тест синхронного view и E2E. MSW остаётся для
   клиентских экранов и клиента.
2. `.dsh/AGENTS.md`, Data and state: открытый вопрос ADR-0004 про data fetching закрыт —
   серверные компоненты, без query-библиотеки, с тонкой границей данных.
3. `.dsh/AGENTS.md`, API client: уточнить, что «UI не вызывает клиент напрямую» означает
   «компоненты не вызывают; вызывает публичная функция слайса `getHomeContent`».
4. Тикет 15: его условие «страница получает данные» надо сузить — 15 генерирует клиент и
   `getHomeContent` (и тестирует клиент через MSW), страницу собирает 16.

### 7. Что это разблокирует

- Тикет 15 — известна точка подключения клиента и что именно тестировать MSW.
- Тикет 16 — известны граница, состояния и что уходит в Playwright.
- Тикет 20 (тестовый контур) — известно, что Vitest нужен для sync view и клиента, а не для RSC.

### 8. Чем подтверждено

Код этим тикетом не менялся; решение не противоречит текущим гейтам. На ветке прогнаны
`pnpm lint` и `pnpm typecheck` — зелёные (фронтенд в состоянии после тикета 12).
