# 18 — Как страница получает данные и где проходит тестируемая граница

Type: grilling
Status: open
Blocked by: 03

## Question

Два вопроса, которые до сих пор не были ни решением, ни тикетом:

1. **Открытый вопрос ADR-0004 про data fetching.** «Server Components, a query library, or a mix» —
   это решение определяет структуру каждого экрана, и при разметке карты я его пропустил.
2. **Ограничение, которое принёс тикет 10.** `async` Server Components **не тестируются** ни в
   Vitest, ни в Jest: оба официальных гайда Next.js говорят об этом прямо и советуют для них e2e.
   При этом правила проекта требуют интеграционный уровень «экран с подменённой сетью через MSW» и
   все четыре состояния. Если страница целиком состоит из async Server Component, этот уровень
   физически не на чем построить.

**Что решить:**

- Где проходит граница данных: async Server Component читает API напрямую, или данные достаёт
  тонкий слой, а экран получает их как пропсы.
- Что именно тогда тестируется Vitest'ом с MSW: синхронная презентационная часть плюс четыре
  состояния, а async-загрузка уходит в Playwright — или граница проводится иначе.
- Кэширование и ревалидация: `fetch` в Next.js, политика кэша, `generateStaticParams` из тикета 12.
- Нужна ли библиотека запросов на клиенте вообще, если данных пока две штуки и они только читаются
  (правило проекта: клиентское состояние — только для клиентских нужд, серверные данные не
  дублируются).
- Стыкуется с пунктом 2 тикета 10: MSW для RSC первоисточниками не подтверждён, поэтому граница
  должна позволять подставить данные, а не только перехватить сеть.

Ответ влияет на тикеты 15 (подключение клиента) и 16 (страница целиком).
